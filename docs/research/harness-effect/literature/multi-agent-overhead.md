# Cost and failure modes of multi-agent orchestration for coding: when delegation pays off and when coordination overhead dominates

## 1. Title and scope

This note compiles verified literature on when multi-agent LLM orchestration improves measured outcomes and when its coordination and token overhead dominates, focused on software engineering tasks. It serves two purposes: to justify concrete, mechanism-level changes to a configuration layer around LLM coding agents (instruction files, hooks, skills, sub-agent routing, stop gates), and to ground a paper on whether such layers change correctness, false claims of completion, cost, and wall time. Every source in section 2 was fetched and read in full text or at its abstract page; claims are quoted or given with their location in the source.

## 3. Synthesis

**What the sources support.** Three claims are consistent across independent groups. First, coordination overhead in multi-agent LLM systems is real, large, and measurable: token multiples of 4x for a single agent and 15x for multi-agent systems in production [2], latency from 1.3x to 117x depending purely on framework architecture [5], the longest trajectories and most correction attempts attributed to coordination overhead in a framework comparison [10], and coordination overhead that "compounds with scale, eventually eliminating parallelization gains entirely" [12]. Second, the gains from multi-agent orchestration are conditional on task structure. Anthropic's own production post states coding "tasks involve fewer truly parallelizable tasks than research" [2]; the information-theoretic analysis proves success decays exponentially with the cut cost of the task's constraint graph and validates this on 14,891 SWE-bench records [6]; scaling studies find diminishing, task-type-dependent returns [13]; and Silo-Bench shows agents gather but fail to integrate distributed information [12]. Third, verification and external feedback are the strongest levers: the only intervention classes with measured gains in the failure-taxonomy study are role clarification (+9.4%) and high-level verification steps (+15.6%) [1]; the theory identifies external execution feedback, not inter-agent communication, as the quantity that can break the information bottleneck [6]; and admission-time verification of shared state accounts for the largest ablated gain in the decentralized design [7].

**What they contradict.** The headline contradiction is between the Anthropic result (multi-agent beat single-agent by 90.2% on their research eval [2]) and the Cognition position (default to single-threaded agents; rule out architectures that violate context-sharing principles [4]). The reconciliation supported by [6], [13] and [12] is that the Anthropic eval is breadth-first research with many independent directions, near the low-C_min regime, while interdependent coding work sits in the high-C_min regime where orchestration loses. A second tension: [2] argues multi-agent systems work "mainly because they help spend enough tokens", yet [11] shows accuracy-only evaluation produces "needlessly complex and costly" agents and that cost-controlled designs can match accuracy at a fraction of cost, which [7] demonstrates concretely ($0.12 versus $0.24 to $0.26 per task at higher resolve rate) and [15] replicates (-$1.18 per instance while improving resolve rate). A third: centralized orchestrator-worker patterns [2] underperform decentralized shared-context designs on identical budgets [7], and forcing parallelism through a central agent actively reduced Pass@2 and Pass@4 in [7]. Meanwhile [3] shows that for well-defined, verifiable subproblems, no communication architecture is needed at all: independent sampling plus majority voting already scales.

**Open gaps.** No fetched source runs single-agent versus multi-agent comparisons at matched token budgets on the same coding benchmark; [7] and [15] come closest by reporting cost, but architectures differ in more than the coordination mechanism. No source measures the effect of instruction-file length or content on agent behavior; only practitioner guidance exists [16], so the configuration layer's most common artifact is unevaluated. No fetched source quantifies false claims of completion (an agent asserting done with failing tests) under different stop-gate designs; [1] documents premature termination and incomplete verification as failure modes but does not evaluate gate mechanisms, and [16] describes hooks without reporting a measured effect. Finally, the failure taxonomy [1] and the theory [6] are complementary but have not been combined: nobody has measured whether failure-mode prevalence predicts a task's C_min, which would give a routing layer a computable signal for when to delegate.

## 4. What a configuration layer should do differently

**Gate the stop on executable evidence, not on agent claims.** The failure modes "unaware of stopping conditions" (12.4%), "no or incomplete verification" (8.2%), "incorrect verification" (9.1%) and "premature termination" (6.2%) together cover over a third of observed failures [1], and the theory says external execution feedback is the only budget that reliably closes the information gap in partitioned work [6]. A stop gate should be a hook that re-runs the test suite or build and blocks termination until it passes, because hooks are deterministic while instruction-file rules are advisory [16]. Concretely: run the smallest verification that covers the diff (affected test files first, full suite only on claimed completion), fail the turn with the captured output pasted back, and cap consecutive blocks (the reference implementation uses 8 [16]) so a genuinely broken change escalates to a human instead of looping forever. Never accept "looks done" from the same context that produced the change; the vendor's own guidance is to require evidence, the test output itself, rather than assertions [16].

**Route by task structure: delegate reads, serialize writes.** Delegation pays when subtasks are independent and verifiable; it loses when constraints cross subtask boundaries, and the loss is exponential in the cut cost [6]. The production data agrees: coding has "fewer truly parallelizable tasks" than research [2], and orchestrator-coupled parallelism reduced exploration diversity in a controlled comparison [7]. The configuration layer should therefore encode a routing policy, not a preference: sub-agents get read-only investigation, localization, and review tasks whose output is a summary or a verdict; all edits to shared or overlapping files run on one agent, serially. Where a decomposition is proposed, a cheap pre-flight check for cross-file coupling (does the diff touch the same files, interfaces, or shared state) decides whether to fan out at all. The effort-scaling table from production practice, 1 agent with 3-10 tool calls for fact-finding up to more than 10 subagents only for complex breadth [2], is a reasonable default routing table to write into the instruction file.

**Cap fan-out, depth, and effort explicitly.** Left unprompted, agents spawn too much: the documented early failure is "spawning 50 subagents for simple queries" [2], step repetition is the single most prevalent failure mode at 15.7% [1], and diminishing returns with agent count are established across task types [13] with overhead that compounds with scale [12]. The layer should enforce hard caps per tier: a maximum number of concurrent sub-agents per lead turn, a maximum delegation depth (two levels is defensible), and per-sub-agent token or tool-call budgets set at spawn time. Effort should scale with measured difficulty, not agent judgment, because agents "struggle to judge appropriate effort for different tasks" [2].

**Share verified state, never raw traces, through a written substrate.** Three independent sources converge on the same mechanism: compact, verified, persistent handoffs beat both prompt-relay through an orchestrator [7] and full-context sharing [4]. The winning pattern in [7] is shared notes typed as FACT, FAIL, or PATCH_SUMMARY, admitted only after verification against evidence, with the verification ablation accounting for the largest accuracy drop when removed. The configuration layer should standardize a scratchpad convention: each sub-agent writes one structured summary (what was tried, what failed with the error, what the fix idea is, evidence that it passed) to a file or artifact, and the instruction file requires reading it before starting. Raw command histories and file dumps must not be relayed; one measured case cut cost from $0.399 to $0.125 on that change alone [7].

**Verify sub-agent output at admission, not at the end.** Merging or relaying unverified sub-agent outputs silently propagates errors: the communication-reasoning gap shows information arrives but is not integrated correctly [12], and unverified shared state corrupted downstream reasoning in the ablation [7]. The layer should run a cheap verifier on every sub-agent result before it is consumed: tests for code claims, a grep or compile for structural claims, and a single strong-model check for review verdicts. Where two sub-agents disagree, that is the signal to escalate to the strong model rather than to average.

**Keep the instruction file short; move conditional knowledge into skills and deterministic hooks.** Overloaded instructions get ignored; the documented rule is that bloated files cause the model to ignore actual instructions, and each line should survive the test "would removing this cause Claude to make mistakes?" [16]. This matches the failure taxonomy, where disobeying task or role specifications traces back to poor specification design as often as model limits [1]. The configuration layer should hold the instruction file to a small, stable core (commands, non-obvious invariants, verification protocol) and push everything conditional into skills loaded on demand, and everything mandatory into hooks. A practical corollary from [16]: if the agent violates a rule repeatedly, first shorten the file and add a hook before adding emphasis.

**Use model tiers for breadth, not for depth; fall back to sampling-and-voting for verifiable subproblems.** The cost-effective heterogeneous pattern is a cheap model on parallel, well-scoped work and a strong model on integration, edits, and final verification: Opus lead with Sonnet subagents [2], and GPT-3.5 intermediates with a GPT-4 finish lifting accuracy from 35% to 47% at lower cost [3]. For subproblems with a checkable answer (localization candidates, test selection, small refactor variants), independent cheap sampling plus majority voting scales accuracy with ensemble size and beats elaborate collaboration frameworks [3]. The layer should define tier roles in the sub-agent configs, reserve the expensive tier for anything that writes code or adjudicates disagreement, and implement voting as a loop over cheap calls with a deterministic aggregator.

**Instrument the layer itself and optimize cost jointly with accuracy.** The evaluation failure mode is optimizing accuracy alone, which produces "needlessly complex and costly" systems and mistaken attributions of gains [11]; architecture alone can swing latency 100x [5] and monetary cost varies widely across frameworks on the same tasks [10]. The configuration layer should log, per feature (hooks, sub-agents, skills), the tokens, wall time, and cost it adds, and should be A/B tested against the baseline agent rather than assumed beneficial. Any new gate or delegation policy should be adopted only if it improves correctness or false-completion rate at equal or lower cost, which is the joint optimization [11] recommends.

## 5. Claims to test

**Experiment 1: cost-matched single versus multi-agent on coding.** Run one strong model single-agent versus the same model with a lead plus capped sub-agents on SWE-bench Verified (300-task random subset, 3 seeds per arm), with both arms budget-capped at equal tokens. Outcomes: resolve rate, tokens per task, wall time, false-completion rate. This tests whether orchestration gains survive budget parity [2], [7], [11]. Rough sample: 1,800 runs.

**Experiment 2: stop-gate ablation against false completion.** Compare three stop conditions on the same 200 SWE-bench Verified tasks, 2 seeds: agent-declared completion, advisory instruction to run tests, and a deterministic stop hook that re-runs the affected tests. Primary outcome: rate of claimed completion with failing tests; secondary: cost added by the gate and premature-termination rate [1], [6], [16]. Rough sample: 1,200 runs.

**Experiment 3: instruction-file length dose-response.** Seed a repo with 15 rule-violating traps and run a fixed task suite under instruction files of 0, 500, 2,000, and 8,000 tokens (50 tasks per arm, 3 seeds). Outcomes: rule adherence rate on the traps, task success, tokens. This tests the practitioner claim that length degrades adherence [16] against the specification-failure evidence [1]. Rough sample: 600 runs.

**Experiment 4: delegation policy under cross-file coupling.** Stratify tasks by a computed coupling signal (files touched by the gold patch that share interfaces or imports), then compare unrestricted sub-agent spawning, read-only-delegation-only routing, and no delegation on 150 tasks per stratum, 2 seeds. Outcomes: resolve rate by stratum, duplicate-work events, cost. This operationalizes the C_min prediction that delegation gains should appear in the low-coupling stratum and disappear in the high-coupling one [6], [13]. Rough sample: 900 runs.

**Experiment 5: shared verified scratchpad versus orchestrator relay.** In a fixed two-tier architecture, have sub-agents either write compact verified FACT/FAIL/PATCH_SUMMARY notes to a shared file or return everything through the lead agent's prompts, on 200 tasks, 3 seeds. Outcomes: cost per task, re-exploration events (same file read twice across sub-agents), resolve rate [7], [4]. Rough sample: 1,200 runs.

**Experiment 6: cheap voting for verifiable subproblems.** On repository localization and test-selection subtasks with checkable answers, compare one strong-model call, eight cheap-model samples with majority voting, and a cost-matched single cheap call (300 subproblems per arm). Outcomes: accuracy per dollar, accuracy at matched cost [3], [11]. Rough sample: 900 subproblem runs.
